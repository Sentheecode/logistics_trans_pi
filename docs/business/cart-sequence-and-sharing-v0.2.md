# SPS 三小车与线内共享澄清 v0.2

来源：2026-11-17 用户语音补充。状态：需求事实与工程建议分开记录；不修改源点表、不绑定新 PLC 写动作、不部署跨机服务。

后续语音确认已并入：首个扫码工位对三台小车分别扫码、分别分拣；相关点位若为 BOOL 就用 false/true，二维码仍为 string。最初提出的“是否只扫描第一台”及“二维码是否改整数”问题已解决，不再重复要求确认。

最新用户明确回复：“代表本台小车的全部分拣完成了。”因此 DB1900.DBX6.0/6.1/6.2 的业务作用域已确认是对应小车在当前工位的本轮全部分拣完成，不是单次放料动作。此问题已关闭，不再重复询问；不将该工位完成等同整条线或整张 SPS 单完成。

## 本轮已确认的事实

1. SPS 分拣区一台 AGV 携带三台小车，不是三台 AGV 各带一台。
2. 首工位按第一台扫码→第一台分拣完成→第二台扫码→第二台分拣完成→第三台扫码→第三台分拣完成的顺序执行；不是只扫第一台取得整组三台数据。
3. 同一条线体由首个扫码工位采集信息，后续工位共享，不重复扫码。语音中的“手工位”结合前文暂记为“首个扫码工位”，不据此新增人工扫码站或指定 140 为首站。
4. 共享既可能不跨 PLC，也可能跨 PLC；同样既可能在同一台上位机，也可能跨上位机。PLC 所属关系不等于共享边界，单进程内存不能满足全部场景。
5. 数值型握手信号按配置写 0/1，BOOL 按类型写 false/true。不能把所有握手硬编码成布尔，也不能把所有结果都转换成整数。
6. PLC→PC：PLC 在自己的地址写入，上位机读取；PC→PLC：上位机写入 PLC 地址。方向以原表逐行声明为准，不仅凭分节标题或 DB 编号推断。

这些信号与三台小车分别对应，用户已确认是当前工位该小车本轮全部分拣完成的反馈。原始名称继续保留为“放料完成”；不能把其他“料仓补料完成”误当成整车完成。

区分两段：扫码完成→读取二维码，是扫码子流程；当前小车分拣完成→处理下一台，是分拣子流程。不能把读取二维码成功直接当作该小车分拣完成，也不能把整车完成信号当成读码完成位已复位的证据。

工程规则草案：当前小车编号 i 与其完成位对应，消费本轮新完成一次后推进，非当前小车位不直接推进当前游标。持续 true 不重复推进，断线/重启/上一次运输残留的 true 不直接认作新一轮完成。采用边沿、周期号还是应答协议，要结合 PLC 清零时机确定，不能只实现上升沿就声称重启可恢复。

完成位由 PLC 写入，PC 读取。原表“上位机给 PLC”中的取料次序为 INT，不能因为存在相同偏移就把它当作这些 BOOL 完成位的复位应答。复位时机在现有表中未描述，保持未定；本轮不写完成位、不改来源方向。

原始 CSV 和读写配对示例保持原样。PC→PLC 的相同偏移不能证明它是对 PLC→PC 信号的复位应答；禁止写只读完成位来“清零”。原表中写分节仍标 PLC→PC 的行按来源保留，不自动赋予写权限。

## 对业务模型的影响

以下是据确认事实提出的设计约束，尚未实现业务数据库或共享 API：

- 区分 AGV、一次运输/到站事件、三台物理小车、小车在本次运输中的顺序、SPS 单和工位。第 1/2/3 台是顺序信息，不直接当作永久小车身份。
- 每个工位按顺序处理三台小车；一次工位完成不能直接视为整条线完成。全线完成及 LWMS 回传的汇总条件仍待定义。
- 共享数据携带来源工位、来源 runtime、关联单据/车辆/小车、版本及持久序号；不能只用 PLC 地址或者一个“当前二维码”全局变量关联结果。
- 小车扫码结果/物料快照可在线内共享，各工位的分拣进度应单独记录。下游处理第一台时，上游可能已在处理后续小车，不能用整条线共用的单一游标覆盖前一台数据。
- 当前未确认具体 AGV 接口里的车辆 ID、任务号、小车码与 SPS 单字段。上面是关联要求，不是臆造外部 API 字段。
- 产线、PLC、上位机实例分别建关系；目前的“外装”等暂作 PLC 对象安排继续保留。新增共享范围映射来表达跨 PLC/跨机情况，不把区域下的全部工位默认共享。

## 跨上位机共享的设计方向（待选型）

先明确共享边界，再选部署方式。当前不预设“所有工位必须共用一个 SQLite 文件”或“必须再建某个云服务”。

- SQLite WAL 继续属于每个 runtime 的本地持久存储，不让多台上位机通过网络共享目录同时直接打开同一个 SQLite 库。
- 扫码采集者对该次结果负责，持久化后按明确关联发布；接收端持久化并去重，重复或乱序消息不能覆盖较新版本。哪些实例负责权威数据、重启接管和共享服务位置，需依据现场部署确认。
- 跨机故障时应区分 PLC 本地采集与业务数据可用性：agent/HMI/对端离线不能连带杀掉 runtime；依赖尚未取得的物料信息时也不能猜测继续执行新业务。具体暂停、补偿和告警策略待业务确认。
- 已有原点表中的机器人心跳、PC 心跳，未来跨机共享服务健康以及 WebSocket 心跳是不同对象，不能互相替代。

共享服务可用性、消息确认、去重、离线重发和恢复需要专门验证，不从当前单进程 mock 成功推导跨机已可用。
