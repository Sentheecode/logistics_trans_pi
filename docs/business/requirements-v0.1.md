# 业务与点位基线 v0.1

来源：用户在本会话提供的信息，2026-11-17。用途：确认理解、保存当前点表、为后续 process/tag 模型提供输入。不是已实现功能或可直接上线的写入配置。

## 确认范围

本项目是工业中间层，上接 LWMS、华睿 AGV、库卡 AGV，下接 PLC。机械臂和相机由 PLC 控制，内部控制不在本项目范围内。通信使用 OPC UA，不因点表含 DB 地址而引入 S7 driver。

仅分拣区 sps、排序区 sort 部署上位机。工位各有归属 PLC，一台 PLC 可以对应一个或多个工位。名称按物料产线命名；按用户指示，外装、仪表一/二、排序一至四暂作为 PLC 配置对象，不推断完整物理产线结构。

已知关系见 `data/baselines/topology.json`：

|---|---|---|
| sps | 外装 | 140、150、160 |
| sps | 仪表一 | 20、30、90 |
| sps | 仪表二 | 40、10、70、80 |
| sort | 排序一 | 210、220 |
| sort | 排序二 | 待补充 |
| sort | 排序三 | 待补充 |
| sort | 排序四 | 待补充 |

工厂字段需求为 id/code/name，但实际值尚未提供。PLC 正式 id/code/name/IP、OPC UA Endpoint 及命名空间未提供，不制造示例生产地址。

## 140 扫码流程：已知与待定

用户确认的顺序：车辆到位完成 → 上位机向对应 PLC 点位写入数值 → PLC 安排相机扫码 → PLC 解析扫码信息并置完成点位为 true → 上位机检测 true 后读取另一个点位取得扫码结果 → 向 LWMS 查询物料信息。

同一条线由首台机械臂扫码，后续机械臂共享信息。共享作用域要显式配置；目前未提供成员与首站映射，不自行认定外装 140 就是首站，也不认定同一 PLC 的所有工位都属于同一共享范围。

| 流程角色 | 当前点表中的候选 | 绑定状态 |
|---|---|---|
| 车辆到位后写入的触发点 | 回复AGV到位 `DB1901.DBX1.0` | 语义吻合但用户未点名绑定，仍需确认；写入值及保持方式未知 |
| 扫码解析完成 | 读码完成 `DB1900.DBX1.5` | 名称吻合；需确认每轮置位/复位规则 |
| 扫码结果 | 小车二维码信息 `DB1900.DBX10.0`，string，原始长度40 | 候选结果点；OPC UA 类型/NodeId 及长度单位待提供 |

只有“顺序”得到确认，不把候选直接变为可执行 process。仍缺：谁清除触发位和完成位、启动时完成位已 true 如何处理、失败/超时、三台小车共享结果地址时如何关联当前车，以及结果在读取期间的稳定性保证。仅完成位为 true 并不证明内存中二维码属于本轮车辆。

工程建议（尚未实现）：每轮扫码有持久 operation_id，绑定工位/车辆到位事件/业务单据与配置版本。协议支持时加入周期号或应答关联；不支持时需明确互斥和复位状态机。网络超时后写入结果不确定，先读回/核对状态，不能直接重发触发。相机失败、PLC 重启、完成位卡住、结果读取到一半等情况不能被当作成功。

## 当前点表的保存规则

`data/baselines/station-140.csv` 是用户确认的当前来源版本，完整保留两个分节、原始名称、DB 地址、类型大小写、长度、方向及说明。只额外加 source_row_id，供引用有重复地址的原始行；它不是现场 tag_id。

- 斜杠 `////////` 表示预留点位，保留地址，但默认不订阅、不写入、不生成报警或 process 绑定；以后启用走配置变更。
- 空名称行仍以空名称保存，标为未命名，不能擅自补成现场功能名。
- 源资料已确认不等于所有字段已具备执行语义。保留来源冲突，不用代码把 DB1900 自动改成 DB1901，不把来源方向按分节标题覆盖。
- BOOL 地址、int/string 的 DBX 记法都是源文档字段，不拿它们替代 OPC UA NodeId。运行配置另存 NamespaceUri、NodeId 标识类型和值、OPC UA 数据类型、AccessLevel、映射审核状态。
- 相同地址可有多条来源记录；配置 tag 的地址别名、重复启用规则需单独确认。预留行不能占用有效业务 tag 的写权限。
- 下层点位带“多层物料不需要”说明，暂不推断当前工位是否启用；工位/物料适用条件待补充。

可复算检查：`python3 scripts/inspect-station-140.py`。该工具只检查保存的来源，不连接 PLC，不改点表，不宣称 OPC UA 地址已验证。重复地址、写分节内仍标 PLC→PC 的行、非 BOOL 的 DBX 地址等作为执行准备项列出，而非擅自修改当前版本。

本次整理共 116 行：PLC 给上位机 66 行，上位机给 PLC 50 行；有名称 75 行，斜杠预留 28 行，空名称 13 行。只读检查发现同分节重复地址 3 组、跨分节相同地址 31 个、写分节中原始方向为读取的行 34 条、非 BOOL 使用 DBX 记法 4 条。它们均在 `station-140-review.json` 引用具体来源行，保留 SHA256 便于识别版本；这些数字不代表 116 个可订阅的唯一 tag。

## 正常自动业务与人工受控写的边界

用户本轮确认：正常业务由 runtime 自动执行。此项细化此前人工受控写规则，不改变三个独立生命周期。确定性业务状态机不依赖 LLM，agent 退出或模型不可用不影响正常业务。

| 动作 | 发起者与授权 | 记录 |
|---|---|---|
| 已审核白名单中的心跳、业务握手、业务回传 | runtime 内部业务状态机，依据配置版本、外部事件及 PLC 状态自动执行 | 状态转换、operation_id、读写结果、配置版本、上下文；心跳按转换/异常与周期摘要记录 |
| 新增/修改 process、tag、地址、动作值、阈值、画面、重试规则 | 维护提案 + diff + 人工确认 + Git 回滚点 + 审计 | 沿用 T1 受控变更协议 |
| 人工补发、强制完成、复位、绕过前置条件 | 尚未授权，不实现通用强制写入口 | 以后逐项定义人工权限与确认语义 |
| 联锁、安全逻辑或对应资源修改 | 始终禁写 | 拒绝并审计 |
| agent 任意写 PLC/调用任意脚本 | 不提供 | 诊断态只读，维护态也不能自行扩大业务白名单 |

不对每次周期性 PC 心跳创建 Git 提交或要求人工点击；配置变更才建回滚提交。正常业务的每次有意义状态转换/非周期动作必须可追踪，但审计不等于重复保存每次心跳电平。白名单内容、点位安全分类及具体握手尚未齐备，因此本轮仅定义边界，不启用写入。

PLC 的“允许 AGV 进入/离开”是 PLC→PC 输入，本项目不能把它写成 true 来制造许可。如何组合该输入、车辆身份和任务状态回复 AGV 尚需接口协议；不声称上位机具备安全控制器功能。

## process 与 tag 的建议模型（待确认）

更新：用户随后明确点位读写两侧要在同一行，地址拆字段，并在名称前增加 code。以 `docs/business/point-table-v0.1.md` 为最新结构依据；同偏移是常见配对线索，不是全量自动合并规则。下文 process/operation 的职责建议仍保留，但不再要求为配置表的两个地址分别建两行。

建议物理拆开，配置查看时联表呈现为旧截图格式：

- tag：一个逻辑点位，保存类型、协议映射、采样/质量、安全分类。来源行单独引用，不能把预留点当有效 tag。
- process：一个动作定义及适用工位/版本，例如扫码、补料、心跳。名称可先整理，FunctionCode 尚未提供，不照搬旧项目 0201/9999。
- process_tag_binding：动作内角色与 tag 的关联，例如 trigger/done/result；序号只定义配置展示次序，不自动等同执行步骤。动作步骤和状态转换另行定义。
- operation：动作的一次实际执行及重启恢复状态；不能把执行实例状态写回静态 tag/process 配置行。
- external_message_inbox/outbox：外部请求去重、回传重试与收发证据的持久记录，消息 ID 和幂等规则需厂商接口文档再定。

这是本次提出的设计建议，不是用户已给定结构；当前不新增业务 DDL，也不安装厂商 SDK。原有 `db/001-infrastructure.sql` 仍是独立采集基础设施草案，不导入这些未完整映射的现场点位。

基础字段建议如下，供下一轮与用户正式 process/tag 结构对齐；不是已建表或擅自新增的现场编码：

| 对象 | 基础字段建议 | 关系/约束建议 |
|---|---|---|
| 工厂 | id、code、name | code 唯一，实际值待提供 |
| 区域 | id、factory_id、code、name | 工厂内 code 唯一；当前仅 sps/sort |
| PLC | id、area_id、code、name、ip、opc_endpoint、配置版本 | 暂用给定名称整理，正式 code 待提供；ip 不代替完整 OPC Endpoint |
| 工位 | id、plc_id、code、name | 编码保存文本；是否工厂内唯一待用户确认 |
| tag | id、plc_id、逻辑编码、名称、类型、读写能力、OPC 映射、来源行引用、reserved、enabled、安全分类、配置版本 | 物理点归 PLC，工位归属及共享通过关联表达，避免三车共享点被重复建立多个写控制者 |
| process | id、编码、名称、动作类型、适用工位、定义版本、enabled | 同一动作多点位；动作类型尚不填入虚构 FunctionCode |
| process_tag_binding | process_id、角色、tag_id、显示序号、配置版本 | 拟表达 trigger/done/result 等；实际角色与绑定需按每种握手确认 |

配置表按用户要求同一行保存 read/write 两组独立字段；driver 仍分别访问两侧实际 OPC 节点，保留各自 quality、时间戳和权限，不能因同一配置行便互相替代读写能力。原始文档方向与服务器能力分别保留。
